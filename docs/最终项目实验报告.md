## 1. 项目简介与最终架构

**解决的问题**：企业自然语言查数中，业务指标口径不明确、复杂 Schema 难以检索、
多表关联容易出错。

**技术路线**：基于 DeepEye-SQL（HKUSTDial，SIGMOD'26，MIT）二次开发，上层用
LangGraph 编排 Agent（ReAct 循环），以 Python 包方式封装 DeepEye 流水线，注入
自建企业知识层（指标口径 / 数据字典 / 外键关系图）与 GraphRAG 检索。

**最终架构（真实调用链）**：

```
用户输入 → FastAPI + SSE（app/web/server.py）
  → LangGraph Agent（app/agent/graph.py，4 节点 ReAct：assistant/tools/
     increment_tool_round/tool_limit，MAX_TOOL_ROUNDS=6）
  → ToolRegistry 6 个工具（app/agent/tools/registry.py）：
     select_data_source / search_metrics / inspect_schema /
     run_text_to_sql / build_visualization / get_capabilities
  → SQLSkill（app/skills/sql_skill.py）：
     值索引守门（_guard_value_index，先于开库）→ 知识增强
     （app/knowledge/enhancement.py：keyword/hybrid + GraphRAG hint）
  → DeepEye 流水线 6 阶段（app/pipeline/）：value_retrieval →
     few_shot_preparation → schema_linking → sql_generation →
     sql_revision → sql_selection
  → SQLite 只读沙箱执行（app/db_utils/execution.py）→ SSE 流式返回
```

**知识层**（`app/knowledge/`）：`models / sqlite_metadata / schema_extractor /
metric_registry / dependencies` 离线构建，`retrieval/` 提供 hybrid、
schema_retriever、join_path（JoinPathFinder）、subgraph（SubgraphExpander）。

## 3. 历史实验详细配置（A–F）

### 实验 A：指标 RAG
- 题单：15 道业务指标问法（开发集）。
- 对照：keyword 检索 vs 关键词+本地向量混合检索。
- 结果：`evals/metric-rag/latest/summary.json` —— keyword `recall@3=0.5667, mrr=0.5667`；hybrid `1.0/1.0`。
- 边界：小规模开发集，指标知识库仅 13 条销售/HR 指标。

### 实验 B：Schema 混合检索（A/B/C/D 四配置对照）
- 命令：`evaluate-graphrag --vector-mode local`（`app/commands/evaluate_graphrag.py`）。
- 配置：A=纯关键词；B=+真实本地向量（Qwen3-Embedding-0.6B，1024 维，CPU）；C=+指标扩展；D=+GraphRAG。
- 结果（`workspace/evals/graphrag-abcd-local.json`）：
  - Column Recall：A 0.7609 → B/C/D 0.8909；
  - Complete Schema Recall：A 0.25 → B/C/D 0.5833；
  - Table Recall：四配置均 1.0。
- 结论边界：**B→C→D 无进一步字段召回增益**；表级召回靠关键词+中文字典已饱和；字段级收益来自混合检索。

### 实验 C：公平 Join 路径对照
- 题单：`evals/adventureworks-graphrag/dev-join.json`，18 题 / 20 条可表示 gold 边。
- 对照：`baseline_shortest`（FK 无权最短路）vs `ours`（JoinPathFinder，评分含外键完整性/基数/来源/粒度/历史区间风险）。
- 结果（`workspace/evals/phase4b/join_paths.json`）：边召回 17/20 = 0.85（双方相同）；Top-1 完整率 1/13（相同）；无关路径 76（相同）；**歧义识别 ours 2/2，基线 0/2**。
- 结论边界：GraphRAG 当前可测量的真实增量是**把无法确定的关系角色显式标为歧义，而不是静默选错**；路径质量本身与最短路打平。

### 实验 D：选择性值索引
- 白名单：`Production.Product / ProductCategory / ProductSubcategory / Sales.SalesTerritory / ProductModel` 的 7 个文本列。
- 本地构建：Qwen3-Embedding-0.6B（1024 维，CPU），110 秒，4.72 MiB，零在线配额。
- 工程能力：白名单严格模式、PII 排除注册表、预算上限（max_values / max_total_values / max_requests）、dry-run 预演、partial 状态显式声明。
- 运行时校验：embedding 签名（v1+v2）、数据库指纹、策略版本三重校验；`incompatible/stale` 拒绝，`partial` 放行。

### 实验 E：混合检索缓存
- 语料指纹缓存（`app/knowledge/enhancement.py` `build_hybrid_index`）：键 = 后端标签 + 文档内容指纹，知识产物一变缓存自动失效。
- 同一问题首次检索 321.9 秒（全部耗在重复编码 595 篇文档）→ 命中缓存 0.63 秒。

### 实验 F：BIRD-dev 消融
- 50 题：仅生成阶段 36/50 (0.72)，完整流水线 38/50 (0.76)。
- 边界：上游 DeepEye-SQL 流水线在 BIRD 上的既有成绩，与本项目 GraphRAG 无关。

## 4. 实验 G：真实在线端到端对照（已完成）

### 4.1 执行背景与授权演进
1. 首轮授权（qwen3.8-max，60k token/run）：三次尝试共 25 次调用，两次暴露真实
   bug（见 4.2），第三次 dashscope 返回 **403 Free quota exhausted**，账户额度耗尽。
2. 经用户批准切换 **kimi-k3.1-pro**（dashscope compatible-mode 托管）：
   - `.env` 三变量切换（`OPENAI_BASE_URL` / `DEFAULT_LLM_MODEL` / `OPENAI_API_KEY`），
     换端点时 extra_body 自动清空，本地 embedding 与值索引签名不受影响。
   - 实测发现该模型**拒绝 temperature 参数**（400 "Parameter 'temperature'... is not
     supported"）→ `LLM.ask` 增加自动去 temperature 重试（`app/llm/llm.py`，
     单测 `tests/test_llm_temperature_fallback.py`，对其他模型零影响）。
3. 60k/run 实测不够（schema_linking 单阶段即 5.5 万 prompt tokens）→ 经用户批准：
   smoke 配置显式精简 revision checker 8→3 个（Result/Syntax/Join，revision 调用
   24→9 次），单 run 上限放宽至 30 万 token。**评测口径注明：本轮在线成绩基于
   3-checker 精简配置**。

### 4.2 执行前的守卫核查与修复（真实发生，均有测试）
1. **核查结论**：token/时间熔断在每次真实 HTTP 请求前检查（`LLM.ask` 入口 +
   while 循环），ContextVar meter 跨线程池共享、锁保护，并行与 tenacity 重试均
   无法绕过；**但 `--max-llm-calls` 只在 band 之间检查，meter 层无调用数硬闸**。
2. **修复 1**：`BudgetMeter` 增加 `max_calls`，与 token/时间同一检查点强制
   （`app/llm/budget.py`），`SQLSkill` 透传，per-run 剩余额度递减分配。新增
   `tests/test_budget_call_cap.py`（8 项）。
3. **修复 2**：预算估算补上 value_retrieval 关键词抽取调用（最坏 41 次/run）。
4. **熔断实战验证**：60k 上限的一轮，baseline 在 sql_generation 阶段以
   `113,506/60,000` 熔断中止——硬闸不是摆设。

### 4.3 qwen 时期三次尝试的记录（保留）

| 尝试 | 消耗 | 结果 | 根因与处置 |
|---|---|---|---|

## 5. 最有价值的真实案例（来自离线评测）

1. **歧义识别（实验 C）**：`Sales.SalesOrderHeader` 对 `Address` 存在
   BillToAddressID / ShipToAddressID 双角色外键。最短路径基线静默选
   `roles[0]`；GraphRAG 把「收货地址所在州」这类问题显式标记为角色歧义
   （2/2 命中）。这是图结构保留多角色边带来的真实能力差异。
2. **复合外键保护（数据资产建设）**：`Sales.SalesOrderDetail` 的复合外键
   （SalesOrderID+SalesOrderNumber）若只用单列 ProductID 关联，行数从
   121,317 膨胀到 296,983（2.45×）；错误 JOIN 放大 23.6×。知识层把复合外键
   完整性写进检索证据与路径评分。
3. **冷启动与缓存（实验 E）**：混合检索首查 321.9 秒几乎全是重复语料编码，
   内容指纹缓存后降至 0.63 秒，且知识产物变更时旧缓存自动失效——缓存正确性
   与性能同时成立。

## 6. 失败案例和技术局限

1. **在线成绩的口径限制**：在线端到端已闭环，但成绩基于 3-checker 精简配置与
   小样本（1 道 dev 题 + 5/12 道封存题）；实验 H 中 Enhanced 与 Baseline 无正确率
   差异，检索层收益**尚未被证明能传导为 SQL 正确率提升**。值索引「构建时配置 vs
   运行时配置」分离曾导致签名失配，已用 v2 路径无关签名修复。
2. **GraphRAG 路径质量未超越最短路**：18 题边召回打平 0.85；差异化只在歧义
   识别与必要中间表解释性。
3. **38 条 AdventureWorks 指标全部未人工审核**（trusted=0），只能作为检索
   证据，不能成为硬 SQL 约束。
4. **评测规模小**：12 道 dev 题、18 道 join 题、6 道封存 test 题——所有百分比
   都只能算初步信号，不构成泛化证明。
5. **AW-JOIN-001/002 双方法 0 命中**：根因在种子召回（0.33/0.5）而非路径
   评分，中文别名映射不足，未及修复。
6. **复杂多步分析任务超出当前架构能力（真实自测失败案例）**：一道「按州×商品
   大类统计销售额/订单去重/历史成本/毛利/同比 + Top-3 增长但毛利率下降」的
   复合任务，8 轮工具上限耗尽后安全停止（3 轮准备 + 3 次 SQL + 2 次可视化，
   其中第 8 轮是第 6 轮的重复重试）。三层根因：① 1 轮 = 1 次工具调用，该任务
   拆解后需 12-15 轮；② Prompt 无反重试约束，轮数被重复提问浪费；③ 运行在
   `enterprise_sales` 库上，该库无历史成本表，历史成本口径根本无法满足
   （需 AdventureWorks 的 ProductCostHistory）。另一设计缺陷：安全停止返回
   `status="success"` + 安抚性回答，掩盖了失败。后续最小改进方向：tool_limit
   触发后强制一次「汇总已有结果」收尾，而非直接 END。
