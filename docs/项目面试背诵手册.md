## 1. 项目介绍

### 30 秒版本

> 我做了一个企业智能数据分析 Agent，解决自然语言查数里指标口径不清、复杂
> Schema 难检索、多表关联易错三个问题。基于 DeepEye-SQL 二次开发，LangGraph
> 编排六个工具的 ReAct 循环，核心是我自建的企业知识层：指标口径、数据字典、
> 外键关系图三级知识，配合关键词+本地向量混合检索和 GraphRAG 关联路径检索。
> 12 道开发题上混合检索把字段召回从 76% 提到 89%；公平对照下 GraphRAG 的
> 真实增量是关系角色歧义识别（2/2 vs 最短路径 0/2）。全链路 FastAPI+SSE
> 流式服务，293 项自动化测试。

### 1 分钟版本

> 企业里业务人员用自然语言查数有三个痛点：同一个指标各部门口径不一致；几百
> 张表的 Schema 模型检索不准；多表关联路径选错导致结果放大或错误。
>
> 我的项目基于开源 SOTA 的 Text-to-SQL 系统 DeepEye-SQL 做二次开发——不重造
> SQL 生成轮子，把精力放在上层 Agent 编排和企业知识层。LangGraph 以 ReAct
> 模式编排指标检索、Schema 获取、SQL 生成、可视化等六类工具；知识层基于
> AdventureWorks 示例库 71 表 486 字段，组织成指标口径、数据字典、外键关系图
> 三级结构。
>
> 检索侧做了关键词+本地向量混合检索和 Table-first/Column-first 双向召回，12
> 道开发题字段召回 76.09%→89.09%；GraphRAG 负责中间表补全、关联路径检索、
> 复合外键保护和聚合粒度风险识别，在公平对照里它的真实差异化能力是关系角色
> 歧义识别。另外针对值索引成本问题做了字段级选择性索引和三重运行时签名校验。
> 系统用 FastAPI+SSE 流式输出，293 项自动化测试全过。

### 3 分钟版本

在 1 分钟版本基础上，按以下顺序展开（每点 30 秒左右）：

1. **为什么不从 0 做 Text-to-SQL**：调研过 Vanna（已停更）、DB-GPT（太重）、
   Dataherald（停更），选 DeepEye-SQL 是 BIRD 榜 SOTA、MIT 协议、Python 包
   形态可封装。我的价值在上层：Agent 编排 + 企业知识注入，这是开源项目没有的。
2. **知识层怎么建**：离线 CLI `build-knowledge` 从 PRAGMA 元数据抽取表/列/外键，
   结合业务指标 JSON 和中文字典，产出结构化知识产物；两次构建字节一致
   （内容指纹验证），152+690 条知识边。
3. **检索怎么融合进生成**：知识以 evidence 文本拼进 DeepEye 流水线入参
   （hint 模式），不裁剪上游 Prompt——保证可对比、可回退。
4. **工程护栏**：值索引三重签名校验、预算 meter 三重硬闸（token/时间/调用数
   都在每次 HTTP 请求前检查）、只读 SQL 沙箱。
5. **诚实边界**：在线端到端已闭环（1 道 dev 题 + 封存集 5/12 次，Kimi K3），
   双组正确率无差异——检索层收益**尚未证明能传导为 SQL 正确率提升**，这句要
   主动说；离线检索评测闭环已完成。

## 3. 核心技术详解

### 3.1 为什么选择知识增强 Text-to-SQL
纯 Text-to-SQL 在企业场景的失败模式不是语法错，而是**业务口径错**（"销售额"
到底是明细求和还是含税口径）和**关联错**（该走明细表还是头表）。模型参数量
解决不了"企业私有语义"——这不是推理能力问题，是知识缺失问题，所以正确解法
是检索注入而不是换更大的模型。

### 3.2 为什么需要企业指标知识库
同一个"净销售额"，财务和销售部门口径可能不同。没有口径知识，模型只能猜聚合
字段和过滤条件。指标条目包含：名称、业务口径描述、formula、涉及表/字段、
时间粒度。当前 38 条 AdventureWorks 指标**全部未人工审核（trusted=0）**，
所以只作为检索证据注入，不作为硬约束——这是有意的安全设计。

### 3.3 指标、表、字段三级知识如何组织
- **指标层**：`adventureworks_metrics.json`（业务口径，人工可审核）。
- **表层/字段层**：`schema_extractor` 从 SQLite PRAGMA 抽取 71 表 486 列 +
  中文字典（`schema_dictionary`）。
- **关系层**：声明外键 → `dependencies.py` 构图，152（企业库）/690（AW）条
  知识边，MultiDiGraph 一条边可带多个业务角色。
- 全部由 `build-knowledge` CLI 离线构建，两次构建字节一致（内容指纹）。

### 3.4 混合检索如何实现
关键词通道（BM 风格打分）+ 稠密通道（本地 Qwen3-Embedding-0.6B，1024 维，
CPU）加权融合。稠密索引按「后端标签 + 语料内容指纹」缓存——知识产物一变缓存
自动失效，保证不给过期向量。

### 3.5 Table-first / Column-first 双向召回
Table-first：先召回相关表，再铺开表内字段——覆盖"问题 mentions 表名或同义词"
的场景；Column-first：直接用字段描述匹配问题——覆盖"问题提到字段但没提表"
的场景。两路合并去重后进 context builder。实验 B 显示表级召回关键词+字典就
饱和（四配置均 1.0），字段级必须靠向量（76.09%→89.09%）。

### 3.6 GraphRAG 如何构图、检索和补全关联路径
图 = 声明外键 MultiDiGraph（保留复合外键和多业务角色边）。检索时种子表出发，
`JoinPathFinder` 搜候选路径，评分维度：外键完整性、基数匹配、来源可信度、
聚合粒度风险、历史时间区间。无法唯一确定业务角色时**显式返回歧义**而不是
静默选 roles[0]。

### 3.7 复合外键、关系角色和粒度风险
- 复合外键：完整保留键组合，单列关联会行膨胀（真实案例 121,317 → 296,983）。
- 角色冲突：BillToAddressID/ShipToAddressID 指向同一张 Address 表，不同问题
  语义选不同边；不确定就报歧义。
- 粒度风险：明细表聚合 vs 头表自带聚合列的口径差异，作为证据写进 hint。

### 3.8 GraphRAG 如何接入 DeepEye-SQL
hint 模式：知识证据作为 `evidence` 文本进入 `SQLSkillRequest`，随 DeepEye
流水线的 dataset 快照流经各阶段，进 SQL 生成的 Prompt。不裁剪上游 Prompt、
不改上游代码——所以 Baseline/Enhanced 可以严格只差一个开关。

### 3.9 选择性 Value Index 如何实现
全量 embedding 71 表 486 列成本高。白名单严格模式：只索引选定的表/列
（5 表 7 列 1,193 值），独立 PII 排除注册表（姓名/邮箱/电话永不索引），
预算上限（max_values/max_total_values/max_requests）构建前校验，dry-run
先出 JSON 预演。未覆盖列运行时降级为"无值证据"，不报错。

### 3.10 Embedding 签名与数据库指纹如何校验
manifest 记录 embedding 签名 v1+ v2（v2 对模型路径做规范化，相对/绝对路径
同模型不失配）、数据库 SHA256 指纹、策略版本。运行时 `verify_runtime_index`
三重校验：换模型 → `incompatible`（拒绝）；改库 → `stale`（拒绝重建前使用）；
策略变 → warning（覆盖变了但向量仍有效）。**校验发生在打开 SQLite 连接之前**，
失败不留锁文件。

### 3.11 缓存如何避免重复语料编码
键 = 后端标签 + 文档集内容指纹。首次编码 595 篇文档 321.9 秒，命中后 0.63 秒。
知识产物任何变化 → 指纹变 → 旧缓存失效，不会喂过期向量。

### 3.12 LangGraph Agent 如何管理状态和工具调用
`AgentState`（TypedDict）携带 messages/model_calls/tool_rounds/tool_trace 等。
条件边 `route_after_model`：有 tool_calls 且轮次未满 → tools 节点；达到
`MAX_TOOL_ROUNDS=6` → tool_limit 节点产出明确超限答复。工具错误包装成
ToolMessage 喂回模型（自愈），全程 tool_trace 留痕。

### 3.13 SQL 沙箱与 SSE 如何实现
沙箱：只读连接 + SQL 前置校验（拒绝多语句、DDL/DML、ATTACH、PRAGMA 写操作）
+ 执行超时 + 行数截断。SSE：Agent 各阶段（知识增强/meter/工具调用）产生
stage 事件流，前端打字机渲染；后端断路靠 BudgetMeter 硬熔断。

## 4. 高频面试问题（40 道）

> 每题格式：**核心回答 → 可能的追问 → 实现依据 → 当前局限**

**Q1 为什么用 GraphRAG 而不是普通 RAG？**
答：普通 RAG 返回孤立的表/字段片段，回答不了"这几张表怎么连"。企业查数
80% 的错误在关联。GraphRAG 把外键关系构图后能输出带角色的关联路径、识别
必要中间表、保护复合外键、标注聚合粒度风险——这些是片段检索结构上做不到的。
追问"提升多少"→ 如实答：路径召回与最短路打平（0.85），增量在歧义识别与
解释性。依据：`app/knowledge/retrieval/join_path.py`。局限：未做图社区摘要
这类原版 GraphRAG 能力。

**Q2 GraphRAG 和最短路径相比有什么优势？**
答：边召回打平 17/20；真实优势两条：① 歧义识别 2/2 vs 0/2——多角色外键
（如 BillTo/ShipTo 同指 Address）最短路静默选 roles[0]，图方法显式报歧义；
② 无关路径少 1 条且每跳带风险评分。不宣称路径质量提升。

**Q3 Table Recall 已经 100% 还需要图检索？**
答：需要。表全对 ≠ SQL 对：中间表遗漏、Join 路径选错、复合外键单列关联、
聚合粒度错都在表级召回之后的环节，这正是图检索覆盖的范围。

**Q4 为什么不直接把全量 Schema 交给模型？**
答：71 表 486 列序列化后数万 token，噪声稀释关键信息且成本高；实验 B 证明
检索式候选（平均 9-12 张表）足够且字段召回可测可控。

**Q5 为什么不用 Neo4j？**
答：当前规模（71 表/690 边）用 networkx 内存图足够，亚毫秒检索；Neo4j 引入
运维成本与部署依赖，收益为零。数据量到万节点级或多跳社区摘要时再考虑。
依据：`app/knowledge/graph_store.py` 基于 networkx。

**Q6 你的独立贡献和 DeepEye-SQL 原生能力有什么区别？**
答：DeepEye 原生：Schema Linking、候选 SQL 生成、revision、selection（BIRD
36/38 of 50 是它的成绩）。我的：企业知识层构建与注入、混合检索+GraphRAG、
选择性值索引、Agent 编排与预算护栏、评测体系。B→C→D 无字段召回增益恰好
说明上游 Schema Linking 强——我的价值在它覆盖不了的业务语义与关联结构。

**Q7 为什么用 hint 而不是直接裁剪 Schema？**
答：hint 可回退、可对照（Baseline/Enhanced 只差一个开关）、不动上游代码；
裁剪 Schema 错杀一张表就是整题失败，且无法归因。先证明知识有价值，再考虑
更激进的注入方式。

**Q8 如何证明检索提升最终改善了 SQL 生成？**
答：如实答：检索层收益（实验 A/B）已闭环；检索→SQL 执行正确率的端到端因果
验证因模型账户额度未完成，这是当前最大的未闭环项。评测入口与协议已就绪。

**Q9 知识库规模多大？数据从哪里来？**
答：两个库：自建企业库（13 指标/11 表/152 边）+ AdventureWorks OLTP 示例库
（微软公开示例，MIT；38 指标/71 表/486 列/690 边）。13 份业务制度文档是
SIMULATED 模拟数据，明确不是微软官方规则。

**Q10 为什么 38 条指标还没有成为可信硬约束？**
答：全部 trusted=0 未人工审核。未审核的口径当硬约束会把错误固化进 SQL——
宁可先当检索证据。审核工作流（review.py）已建，缺的是业务专家确认这一步。

**Q11 如何处理 Embedding 模型变化和索引失效？**
答：manifest 记录签名 v1+v2 + 维度 + 模型名；运行时校验，换模型直接
incompatible 拒绝，绝不拿新模型向量查旧索引。v2 对路径规范化，相对/绝对
路径同模型不误判。真实教训：v1 把路径烤进哈希，运行时路径展开后失配，
我们离线重建索引补齐 v2（零在线成本，17 秒）。

**Q12 线上调用成本和冷启动问题如何解决？**
答：三重 meter 硬闸（token/时间/调用数，每次 HTTP 请求前检查，并行/重试
不可绕过）；两道在线门（--approve-online + 具体上限）；知识检索侧语料指纹
缓存（321.9s→0.63s）；本地 embedding 零 API 成本。

**Q13 为什么要选择性建立值索引？**
答：值索引用于"问某个具体值在哪些表出现"。全量 486 列成本高且大部分列
（外键 ID、时间戳）没检索价值。白名单+PII 排除+预算上限+dry-run，5 表 7 列
1193 值 110 秒 4.72MiB。不做全库对照，不宣称节省比例。

**Q14 实验没有提升时，你如何解释？**
答：先归因再说话。实验 C 打平就如实写打平，把增量定位到歧义识别；AW-JOIN-001/
002 双 0 命中，归因分析定位到种子召回（0.33/0.5）而非路径评分——错误归因
比错误结果更危险。

**Q15 LangGraph 为什么选它而不是 LangChain Agent / 自己写循环？**
答：需要的是显式状态机（轮次上限、条件路由、状态持久化）而非黑盒 Agent
执行器；LangGraph 的图定义刚好匹配，且后续可加 interrupt 做 HITL。

**Q16 Agent 最多 6 轮工具调用，会不会不够？**
答：6 类工具常规问法 2-4 轮收敛；超限走 tool_limit 节点给明确答复而不是
无限烧钱。轮次数是显式常量，可按场景调。

**Q17 工具调用失败怎么处理？**
答：异常包装成带 error status 的 ToolMessage 回喂模型，模型可修正参数重试；
全程 tool_trace 记录，失败不静默。依据 `ToolRegistry.invoke`。

**Q18 SQL 执行的安全怎么保证？**
答：只读连接 + 语句白名单前置校验（拒多语句/DDL/DML/ATTACH/PRAGMA 写）+
超时 + 截断。测试里有专门用例（`test_sql_skill.py`）。

**Q19 混合检索权重怎么定？**
答：weighted 融合，当前经验值。诚实答：没有做权重网格搜索，是明确局限。

**Q20 本地向量为什么不用 API embedding？**
答：企业场景数据不能出域；本地 Qwen3-Embedding-0.6B CPU 可跑（索引构建
110 秒），零 API 成本，1024 维质量足够字段级召回。

**Q21 评测题怎么来的？会不会泄漏？**
答：dev 12 题 + join 18 题 + 封存 test 6 题，test 集 generation 后隔离、
本轮之前从未参与任何调优；检索器禁止读取 required_tables/gold 边（代码
层面隔离，evaluate_graphrag 有封存保护）。

**Q22 怎么防止检索器用评测答案作弊？**
答：检索器输入只有问题文本；gold 边分类（representable/unreachable）只在
评分侧使用；同义改写题验证泛化。

**Q23 BIRD 72%→76% 是你的贡献吗？**
答：不是。那是上游 DeepEye 流水线的公开成绩，我们只在上面做增量，报告里
明确切割归因。

**Q24 知识层构建的可复现性怎么保证？**
答：CLI 一次构建全部产物，两次构建字节一致（内容指纹排除时间戳字段）；
产物 gitignore 但有 PROVENANCE 记录来源与哈希。

**Q25 遇到的最难的技术问题是什么？**
答：真实案例：值索引签名在"构建时相对路径"与"运行时绝对路径"两处口径
不一致，在线首跑 prepare 阶段崩溃。定位到签名 v1 把路径烤进哈希的设计缺陷，
补 v2 规范化路径 + 离线重建，并补了能区分异常类型的回归测试（旧测试只看
error/prepare，两类异常都过——测试断言不够精确也是一种 bug）。

**Q26 并行请求会不会绕过预算限制？**
答：meter 是 ContextVar 持有的同一对象，线程池 copy_context 复制的是引用，
加锁累计；check() 在每次真实 HTTP 请求前执行，并行与 tenacity 重试都会
重新过闸。

**Q27 如果模型返回空内容/被 max_tokens 截断怎么办？**
答：所有 choice 空内容且 finish_reason 全是 length → TruncatedResponseError
快速失败（重试同输入是确定性浪费）；部分有效则保留有效 choice 补采。
依据 `app/llm/llm.py`。

**Q28 中文字段描述从哪来？**
答：schema_dictionary：表/列的中文名与同义词映射，人工维护 JSON；这也是
表级召回关键词就能饱和的原因。

**Q29 上下文 token 成本如何度量？**
答：enhancement observability 记录 context_tokens；usage ledger 记录每阶段
prompt/completion tokens（SQL_USAGE_LEDGER）。

**Q30 SSE 流式输出流的是什么？**
答：阶段级事件（stage started/completed/failed、meter 快照、工具调用轨迹）
+ 最终结果，不是 token 级补全流。

**Q31 为什么选择 SQLite 做企业库载体？**
答：示例库分发简单、只读沙箱好实现、SQL 方言标准；AdventureWorks 原版是
SQL Server，移植时 Schema 点号表名（"Sales.SalesOrderHeader"）、TEXT 存
DECIMAL、日期 TEXT 三个坑都有显式适配层。

**Q32 复合外键错误关联的代价能具体说吗？**
答：SalesOrderDetail 若只用 ProductID 单列关联，行数 121,317 → 296,983
（2.45×）；一个错误 JOIN 放大 23.6×。这类反例被做成评测资产验证检索器。

**Q33 项目里你写过多大的代码量 / 哪部分最自豪？**
答：自豪的不是量而是三个"防御性设计"：签名校验先于开库、预算闸在请求前、
歧义显式返回。每个都被真实故障验证过价值。

**Q34 如果重新做，你会改什么？**
答：① 先跑通在线端到端再优化离线检索（本轮教训）；② 签名 v2 一开始就做，
不留 v1 兼容包袱；③ 指标审核流程前置。

**Q35 在线实验做出了什么？**
答：真实在线端到端已跑通（Kimi K3）：1 道 dev 题 Smoke 双组成功且结果均正确，
Enhanced 注入 1,982 字符 GraphRAG 知识证据、token 仅 +4.9%；封存 test 集 6 题
完成 5/12（2 题双组正确、1 个 baseline 真实失败样本），累计 49 万 token。成绩
基于 3-checker 精简配置与小样本，只作初步效果，不宣称提升。

**Q36 团队协作 / 独立完成？**
答：独立完成；基于的开源上游（DeepEye-SQL）只做封装不改源码，所有增量
在自己目录（app/knowledge、app/vector_db、app/commands、app/agent）。

**Q37 486 列的中文字典覆盖率？**
答：字典覆盖有统计（dictionary_coverage 进评测产物）；未覆盖列走原名与
描述回退。具体数字见 graphrag-abcd 产物。

**Q38 为什么指标评测用 Recall@3 而不是 Recall@1？**
答：指标条目会多条注入 Prompt，Top-3 覆盖即可用；MRR 一起报以看排序质量。

**Q39 线上如何监控坏案例？**
答：每请求落盘 artifact（dataset 快照、error.txt 脱敏、usage ledger、
value_index_status），可离线重放；tool_trace 全留痕。

**Q40 项目最大的风险/不足？**
答：三点：① 在线样本小且双组无正确率差异，检索收益到 SQL 正确率的传导未被
证明；② 38 条 AW 指标全部未人工审核（trusted=0），只能做检索证据；③ K3 下
单 run 12 万+ token（97% 在 prompt 端），成本工程是真实短板——这正是值索引、
预算硬闸和未来小模型短路优化的动机。

## 5. 简历最终版本（4 条，全部有真实产物支撑）

**项目：基于 GraphRAG 的企业智能数据分析 Agent（Text-to-SQL）**
技术栈：Python / LangGraph / DeepEye-SQL / FastAPI+SSE / networkx / Qwen3-Embedding / SQLite

1. 基于 DeepEye-SQL（BIRD 榜 SOTA）二次开发企业数据分析 Agent，以 LangGraph
   编排 4 节点 ReAct 循环与 6 类工具（数据源选择/指标检索/Schema 检查/Text-to-SQL/
   可视化），FastAPI+SSE 流式服务，自动化测试 293 项全通过。
2. 构建企业三级知识层（指标口径 / 数据字典 / 外键关系图，覆盖 71 表 486 字段、
   690 条知识边），设计关键词+本地向量混合检索与 Table-first/Column-first 双向
   Schema 召回，12 道开发题字段召回率 76.09%→89.09%，完整 Schema 召回
   25.00%→58.33%；指标检索 Recall@3 0.5667→1.0000（15 题开发集）。
3. 实现 GraphRAG 关联路径检索（JoinPathFinder）：多角色外键边建模、复合外键
   完整性保护、聚合粒度风险评分；与无权最短路径公平对照（18 题/20 gold 边）
   边召回打平（17/20），差异化能力为关系角色歧义识别（2/2 vs 0/2）与路径
   风险解释。
4. 设计字段级选择性值索引（白名单/PII 排除/预算上限/dry-run）与运行时三重
   校验（embedding 签名 v1+v2 / 数据库指纹 / 策略版本），配合语料指纹缓存
   将混合检索冷启动 321.9s 降至 0.63s；实现 token/时间/调用数三重预算硬闸
   （每次模型请求前强制检查，支持并行与重试场景）。

> 使用注意：第 2 条数字是检索层离线评测；在线端到端（实验 G/H）双组正确率
> 无差异，如实表述为「端到端闭环已跑通、检索证据确认进入生成输入，但小样本下
> 不构成准确率提升的证据」（见实验报告第 4 节）。
