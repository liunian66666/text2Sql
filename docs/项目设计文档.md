# 智能数据分析助手 —— 项目设计文档

> 定位：面向 Agent 开发实习岗位的工程型项目。核心叙事不是"做了一个 Text-to-SQL 模型"，
> 而是"构建了一个具备路由决策、工具调用、反思自愈、人机协同、经验记忆与评测闭环的数据分析 Agent"。
> Text-to-SQL 生成内核 fork 开源 SOTA（DeepEye-SQL，SIGMOD'26，MIT），自己做上层 Agent 编排与优化。

## 1. 项目定位与面试叙事

一句话：**基于 LangGraph 的数据分析 Agent，Router-Skill 架构，NL 提问直达 SQL 执行与可视化，
集成执行反思自愈、澄清反问（HITL）、自学习记忆与置信度路由，全链路可观测、可量化评测。**

面试可展开的六个 Agent 工程知识点（每个都对应本项目的真实模块）：

| Agent 核心概念 | 本项目对应模块 | 关键设计问题（会被问） |
|---|---|---|
| Workflow vs ReAct 编排 | LangGraph 主图：Router → Skill | 为什么查数用 workflow、闲聊用 ReAct？确定性 vs 开放性的取舍 |
| 工具调用抽象 | SQL 执行、schema 检索、图表生成均为 Tool | 工具入参出参设计、失败契约、超时与只读安全 |
| 反思 / 自我纠错 | SQL 执行失败 → 报错回传 → 修复重写 | 重试上限、错误信息如何结构化喂回、何时放弃升级 |
| Human-in-the-loop | 歧义检测 → 反问澄清 → 用户回答续跑 | LangGraph checkpoint/interrupt 的用法、状态持久化 |
| Agent 记忆 | 自学习飞轮：已验证 Q-SQL 对回灌 few-shot 索引 | 记忆的写入条件、去重、失效（schema 变更后淘汰） |
| 评测与可观测 | 固定验证集 EX 回归 + LangSmith trace | 怎么证明优化有效、成本/延迟怎么量化 |

## 2. 分层架构

```
用户提问
   │
   ▼
[应用壳 · 全部自写]  FastAPI(SSE流式) + LangGraph 主图
   ├─ Router 节点：意图分类（查数/排名/趋势/占比/闲聊），小模型或规则+LLM 混合
   ├─ 歧义检测节点：置信度低 → interrupt 反问（HITL），LangGraph checkpoint 续跑
   ├─ 置信度模型路由：简单题走小模型直出 SQL，难题才进深度 pipeline（降本）
   ▼
[技能层 · 核心 fork]  DeepEye-SQL 封装为一个 Skill（不是黑盒，是编排进图的子流程）
   ├─ grounding / schema linking   ← 优化点B：MDL 业务口径注入
   ├─ N-version 候选生成            ← 优化点A：few-shot 索引回灌（自学习）
   ├─ 工具链测试 + 修复             ← 复用其 syntax/logic/quality checker
   └─ 执行感知候选选择              ← 优化点C：置信阈值自适应
   ▼
[执行层 · 自写]  SQLite 只读执行器（超时/行数上限/AST 校验）
   ▼
[输出层 · 自写]  结果表格 + 自动可视化（柱/折线）+ SQL 展示与自然语言解释
```

依赖技术栈：Python 3.13、FastAPI、LangGraph、ChromaDB（上游同款）、SQLite、LangSmith、uv。

## 3. Fork DeepEye-SQL 的集成方式

- 仓库：https://github.com/HKUSTDial/DeepEye-SQL（MIT，uv 管理，ChromaDB 向量索引，OpenAI 兼容 LLM 接口）
- 不做黑盒 subprocess 调用；以 **Python 包依赖 + 重封装** 方式接入：
  1. 保留其 `app/` pipeline 作为 SQLSkill 内部实现；
  2. 在其四个 stage 边界暴露 hook（它本身是 stage 化代码 + structured snapshot，天然可切）；
  3. 每个 stage 包一层 LangGraph node，使中间状态可 trace、可中断、可回放。
- LLM 统一走 OpenAI 兼容端点（dashscope/GLM 均可），配置进 `.env`。

## 4. 优化点（Agent 叙事优先，全部可量化）

按优先级实施，每个优化点完成后在固定验证集上跑 EX 回归、记录增量：

1. **自学习记忆飞轮（Agent 记忆叙事）**
   - 上游 `app/few_shot/` 已有 dynamic few-shot 索引，接口现成；
   - 写入条件：SQL 执行成功 + 结果非空 + 用户点击"答案正确"确认；
   - 量化：同域问题重复场景下 few-shot 命中率与 EX 随使用次数的增长曲线。
2. **MDL 业务口径层（Context Engineering 叙事）**
   - 轻量 JSON：指标名 → SQL 口径、维度、合法连接路径；
   - 注入 grounding 阶段的 prompt 组装；替代原方案"业务黑话 RAG 索引"；
   - 量化：含业务黑话的测试子集 EX 增量。
3. **歧义澄清回路 HITL（人机协同叙事）**
   - Router 后加歧义检测（候选口径不唯一/时间范围缺失/排序指标缺失）；
   - LangGraph `interrupt` + checkpointer 实现反问-续跑；
   - 量化：歧义子集上"错误猜测率"下降与澄清后正确率。
4. **置信度路由与降本（成本工程叙事）**
   - 复用上游执行结果聚类的置信信号：高置信 → 短路 + 小模型；
   - 量化：平均 LLM 调用次数、每题成本、P95 延迟 vs EX 的 trade-off 曲线。

暂不做：跨方言（Spider2 场景）、微调 SQL 模型、处理 benchmark 金标错误。

## 5. 评测方案

- 验证集：BIRD-dev 抽 150～200 题（SQLite、含业务证据）+ 自建业务库 50 题（含黑话/歧义/空结果用例）；
- 指标：EX（主）、澄清触发正确率、平均调用次数/成本/延迟；
- 基线：fork 原版 DeepEye-SQL 先跑通出基线分，之后每个优化点一个增量条目；
- 产出：`evals/` 目录（验证集、runner、结果表 `results.md`），面试可直接展示。

## 6. 里程碑

| 阶段 | 内容 | 验收 |
|---|---|---|
| M1 | clone 跑通 DeepEye-SQL，BIRD 子集复现基线 | 基线 EX 表 |

## 7. 风险

- fork 上游依赖/LLM 端点兼容问题（M1 第一周即暴露，好解决）；
- few-shot 回灌污染：schema 变更后旧样本失效——需实现按 schema 版本淘汰；
- 优化点若无增量 EX：保留消融实验记录，"负结果+原因分析"同样是面试素材。
