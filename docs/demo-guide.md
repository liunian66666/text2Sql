# DeepEye-SQL 演示站说明（答辩用一页纸）

本地单用户演示入口：企业数据分析 Agent + 离线评测结果浏览。只读数据库、串行任务队列，不启动任何评测任务。

## 启动

```bash
# 在项目根目录 DeepEye-SQL/ 下执行；首次先同步依赖
uv sync
uv run python -B runner/run_demo.py --check-only
uv run python -B runner/run_demo.py

# uvicorn 零参工厂方式（不支持 --config，用默认配置或环境变量 CONFIG_PATH）
uv run uvicorn app.web.server:create_app_from_env --factory --port 8000
```

`uv run` 默认会确认锁文件与虚拟环境一致，适合首次启动和换机器复现。只有已经执行过 `uv sync`、并且明确不希望 uv 再检查依赖时，才需要可选的 `--no-sync`。

配置来源按 **shell 环境变量 > 仓库根目录 `.env` > TOML** 叠加；把密钥写进 `.env`（`cp .env.example .env`）同样可用，`--check-only` 会显示是否命中 `.env`（只报变量个数）。

浏览器打开 <http://127.0.0.1:8000> 即可。可选参数：

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `--config` | `config/local/demo-fast/config-bird-demo.toml` | 快速演示配置（缺失时兼容回退到50题配置） |
| `--host` | `127.0.0.1` | 仅本机访问；答辩需要局域网投屏时改 `0.0.0.0` |
| `--port` | `8000` | 端口被占用时换一个，如 `--port 8010` |

启动前确认：`--config` 指向的配置文件里模型服务可达（可用 `curl <base_url>/models` 自检）。

当前 `demo-fast` 配置使用 `deepseek-v4.1-flash-1017`；下方 2026-10-27 的历史实测仍保留当时 `deepseek-v4-pro-0813` 的模型标注，切换模型后不可直接横向比较耗时和 token。

## 页面结构

- **单题在线演示**：默认自动识别销售 / HR 业务域，也可手动指定数据源 → 选示例问题（或手输）→ 可填证据口径 → 开始分析。手动选择优先于自动判断，结果区会显示实际使用的数据源。
  LLM Planner 根据对话和工具描述决定调用业务口径、Schema、Text-to-SQL 或可视化工具；工具结果返回模型继续规划，最终展示 Agent 结论、工具轨迹、SQL、阶段耗时、Token、结果表与图表。
  进度条上前三格是 Agent 自己的循环：**LLM 规划**每轮模型调用各亮一次、**工具调用**每次工具执行各亮一次、**规划与编排**从请求开始亮到请求结束（它的耗时 = 总墙钟 − SQL Skill 自己的秒表，所以常是最大的一格）。
- **离线评测结果**：自动识别三类报告：Text-to-SQL 三档消融、Agent 专项通过率、业务口径 RAG Recall/MRR。报告只读展示，现场不触发昂贵评测。

## 企业库端到端实测（2026-10-27，DashScope deepseek-v4-pro-0813 + qwen3.7-text-embedding-flash，已关思考）

| 类型 | 结果 | Agent 墙钟 | SQL Skill | Token（Skill chat + embedding + Planner） | 图表 |
| --- | --- | --- | --- | --- | --- |
| 查数（销售额/订单量/客单价） | success | 60.3s | 48.8s | 36,336 | 指标卡，1 行 |
| 排名（Top10 商品） | success | 62.2s | 49.9s | 36,176 | 柱状图，10 行 |
| 趋势（按月） | success | 57.6s | 44.9s | 35,517 | 折线图，12 行 |
| **平均** | 3/3 成功 | **60.0s** | **48.5s** | **36,010 / 题** | 27 次 chat 调用，0 次失败尝试 |

阶段平均耗时：值检索 5.1s · Few-shot 24.0s · Schema Linking 5.6s · SQL 生成 13.1s · 修订 0.0s · 选择 0.0s · Agent 规划与工具编排 12.2s。Few-shot 是当前最大的一段（预备 SQL 两次采样 + 目标掩码一次），演示时进度条在这一段停留最久。

三题的修订与选择均为 **0 次模型调用**：三路生成的候选执行结果一致，选择走 `候选数 ≤ 1` 捷径、修订无错误模式可修。所以这三题适合演示"链路稳定"，不适合演示"修订纠错"；纠错请看 50 题离线对照页。

结果核对方式：企业库是合成数据、没有 BIRD 金标 SQL，因此不声称 EX 准确率。用「JOIN 后直接聚合」与「先按订单聚合再求和」两种写法对 `enterprise_sales.sqlite` 独立复算，得到相同的 **2,513,691.692 元 / 453 单 / 5,548.99 元客单价**；2026 年状态分布 367 completed + 44 paid + 42 shipped = 453，36 笔 cancelled 被正确排除。

> 历史数据：2026-10-26 那组"3 题 41.62 秒 / 153,436 Token、集合式 EX 3/3"是在自建端点 + text-embedding-v4 下跑在 BIRD 库上的结果，保存在 `evals/demo-fast/`。切换模型和向量后它不代表当前配置，且当时"思考输出无法关闭"的结论只适用于自建端点。

## 演示流程建议（约 8 分钟）

1. 先用闲聊问题展示 Agent 路由，说明它不会把所有输入都送进昂贵的 Text-to-SQL 流程。
2. 跑一个销售趋势或排名问题，讲 LLM 规划 → 工具调用 → 指标口径 → Schema Linking → SQL → 图表的完整链路。
3. 再跑一个 HR 问题，强调不修改 Agent 主流程即可新增业务域，并展示自动选库和指标隔离。
4. 在任意长任务跑到一半时刷新一次页面，展示“刷新不取消任务、不重复提交、进度自动恢复”（详细步骤见下一节）。
5. 打开**离线评测结果**页，展示 50 题三组消融、15 题 RAG 对照、14 题 Agent 专项及 HR 6 题结果，说明准确率、耗时、Token 和已知边界。

## 刷新与换页恢复演示步骤（约 3 分钟）

任务跑在服务端线程里，浏览器只是订阅者，**刷新页面既不取消任务，也不会重新提交**。演示顺序：

1. 提交一个耗时较长的问题（如 Top10 商品排名），等进度条走到 **Few-shot** 或 **Schema Linking**。
2. 按 F5 刷新页面。页面顶部显示“正在恢复上一次任务……”，问题气泡与进度卡片重新出现，随后变成“任务仍在后台执行，已恢复进度连接”。
3. 证明“没有第二次提交”有两种方式，任选一种：打开浏览器 DevTools → Network 面板，整个刷新过程只会出现一条 `POST /api/chat`（刷新后是 `GET /api/query/{id}` 与 `GET /api/query/{id}/events`）；或看 `workspace/demo_tasks/` 目录，全程只新增一个 `<request_id>.json`。
4. 等任务结束，结果、图表、表格、SQL、耗时与 Token 全部照常出现——这些是刷新后从 `GET /api/query/{request_id}` 回填的，不是重新算的。
5. 再刷新一次（此时任务已完成）：直接显示“上一次任务已经完成，结果已恢复”，不建立 SSE 连接。
6. 紧接着输入“做成柱状图”：`conversation_id` 与刷新前一致，追问复用上一轮结果，不重新执行 SQL。
7. **新开一个标签页**（Ctrl+T 输入 `http://127.0.0.1:8000`）：这个页面的 `sessionStorage` 是空的，但它会问一次 `GET /api/query/active`，发现服务端有任务在跑，于是直接接手同一条进度（沿用原 `conversation_id` 与数据源）。此时两个标签页都能看到进度，而队列里始终只有 **一个** 任务。
8. 任务结束后再新开标签页：`active` 返回 `null`，页面显示普通欢迎页——跨标签页不追溯已结束的历史结果，避免变成会话中心。
9. 想看中断态：任务运行中按 Ctrl+C 停掉服务再重启，刷新页面会显示“后端在任务执行期间重启，本次任务未完成，请重新提交”，问题文本留在输入框里，不会无限加载也不会自动重提。

恢复期间发送按钮、数据源下拉、新建对话与推荐问题都被禁用，避免在旧任务上再排一个新任务。`sessionStorage` 只保存 `request_id`、`conversation_id`、问题文本、`database_id`、创建时间与事件游标，不保存 SQL 结果、模型原始响应、密钥或绝对路径。

- Agent 首轮在线评测：11/14；修复意图边界和新客户口径漏检后，原两项功能失败均通过。
- 当前增量合并报告：14/14；最后一题切换到 `deepseek-v4.1-flash-1017` 后复测通过。该数字复用了首轮已通过结果，不表述为新模型整批 14 题成绩。
- HR 第二业务域：6 个固定端到端问题 6/6；均自动选择 HR、命中正确指标并与可信 SQL 结果一致。增量合并记录平均 67.35 秒/题、总计 241,264 Token。
- 销售域回归：自动选择销售库，2026 年有效订单数 453 与可信 SQL 一致，1/1。

## 排查

| 现象 | 处理 |
| --- | --- |
| 提交后长期停在“排队/运行中” | 模型服务被 50 题评测占满时会排队，属正常；评测结束后变快。看 `workspace/demo_server.log` 是否有 `retry` 告警 |
| 某阶段红色“失败” | 结果区会显示 `failed_stage`；先 `curl <base_url>/models` 确认模型服务在线，再换推荐问题重试 |
| 刷新页面丢了进度 | 正常情况下不需要处理：页面会自动用原 `request_id` 查状态并重连。若显示“任务记录已失效”，说明后端已没有该任务（超过清理周期或换了机器），重新提交即可；也可手动访问 `GET /api/query/<request_id>` 核对 |
| 新标签页没有接手正在跑的任务 | 先确认服务是新代码（`GET /api/query/active` 应返回 `{"task": {...}}`，旧进程会 404）。若返回 `{"task": null}`，说明任务其实已经结束——跨标签页只接手 `queued` / `running`，不追溯已完成的历史结果 |
| 刷新后显示“后端在任务执行期间重启” | 这是 `interrupted`：进程重启时任务队列只在内存，未完成的 `queued` / `running` 记录会被标记为中断。问题文本已填回输入框，点发送重跑一次即可，不会自动重复提交 |
| 端口被占用 | `--port 8010` 换端口重启 |

安全边界：数据库仅服务端白名单注册；SQLite 只读连接 + authorizer 拦截写操作；执行超时与最大行数在页面上可调但服务端有上限；页面不回显密钥、绝对路径与堆栈。
