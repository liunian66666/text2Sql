# 复杂查询 Agent 执行效率与任务完成率修复报告

> 生成时间：2026-11-13。对象：真实前端一次复杂经营分析请求
> （143.5 秒 / 9 次模型决策 / 达到步数上限 / 仅返回订单日期范围 / 前端显示"分析完成"）。
> 全部结论来自 `workspace/state/agent_state.sqlite` 的 task 记录、`workspace/skill_requests/`
> 的流水线产物与三次真实在线回归（`workspace/evals/fix-complex/`），不基于页面猜测。

---

## 1. 真实失败根因（逐条有证据）

### 1.1 现场还原（task 记录，2026-11-13T10:03Z）

| 轮 | 工具 | 结果 | 说明 |
|---|---|---|---|
| 1 | search_business_metrics | **failed** | 未选数据源就检索口径，白耗一轮 |
| 2 | select_data_source | completed | 选了 `enterprise_sales`（**该库没有历史成本表**） |
| 3 | search_business_metrics | completed | 13 条电商指标，无历史成本口径 |
| 4 | inspect_database_schema | completed | — |
| 5 | run_text_to_sql | completed | **用完整六阶段流水线跑一条 `SELECT MIN(order_date), MAX(order_date) FROM orders`** |
| 6 | run_text_to_sql | completed（**未真正执行**） | 被"本轮 SQL 已生成"守卫拦下，只回一句提示 |
| 7 | build_visualization | completed | 表格 |
| 8 | run_text_to_sql | completed（**未真正执行**，与第 6 轮几乎逐字相同） | 同一守卫拦下 |

- 累计 token 中该次 SQL Skill 一次就烧掉约 5.6 万（few_shot 30.7s + schema_linking 29.0s +
  generation 32.8s），产出只是一个两列的日期范围。
- 最终 `result.sql` = 第 5 轮的日期探查 SQL，`result.rows` = `[['2025-01-02','2026-12-31']]`，
  `status = success`、`failed_stage = None` → 前端判定"分析完成"。

### 1.2 五条真实根因

1. **`select_data_source` 的工具枚举被硬编码为两个企业库**（`app/agent/tools/source_tool.py`
   的 `Literal["enterprise_sales","enterprise_hr"]`），即使 AdventureWorks 注册成功，
   Agent 在 schema 层也无法选择它。再加上本机 `.env` 没有 `ENABLE_ADVENTUREWORKS`，
   实际运行进程里根本不存在该数据源。
2. **没有数据源能力判定**：`enterprise_sales` 无 `ProductCostHistory` 之类的成本历史表，
   Agent 仍在该库上尝试"历史成本"，只能退化成当前标准成本（模型在 SQL 说明里自己写了
   "数据库无历史成本表"），属于口径失真而非能力缺失提示。
3. **确定性事实走完整 Text-to-SQL 流水线**：`MIN/MAX(order_date)` 这种元数据问题，
   被当成业务 SQL，花掉约 5.6 万 token、90 秒。
4. **一轮只允许一次 SQL 的硬限制**：`_run_text_to_sql` 中
   `sql_result_turn_id == turn_id` 即返回"禁止再次调用"。日期探查占用了整轮唯一的 SQL
   预算，真正的经营分析 SQL 永远没有机会执行；第 6/8 轮看似执行、实则被拦截。
5. **终止状态被 skill 结果覆盖**：`tool_limit` 节点设置了 `agent_error`，但 service 在
   有 `sql_result` 时用 `**skill` 合并结果，`failed_stage` 被 skill 的 `None` 覆盖，
   `status` 仍是 `success` → 前端无法区分"部分完成"与"分析完成"。
   另外 `probe` 类中间结果与业务结果没有隔离，日期范围被当作最终查询结果。

附带：模型第 6、8 轮重复提交同一子问题，说明缺少重复调用检测与计划约束。

## 2. 修改文件与核心实现

| 文件 | 改动 |
|---|---|
| `app/agent/capabilities.py`（新增） | 基于真实 `PRAGMA` 元数据做能力识别：`historical_cost`（要求成本列 + 生效起止日期）、`ship_address`、`product_hierarchy`；`required_capabilities()` 只认业务措辞，不猜 |
| `app/agent/tools/probe.py`（新增） | 白名单只读探查器：`date_range` / `row_count` / `distinct_values` / `exists`；表名字段名必须来自真实 Schema，SQL 由模板拼装，`PRAGMA query_only`，敏感字段禁查；`last_complete_year()` 同时校验年初与年末覆盖，区分现实时间与库覆盖时间 |
| `app/agent/tools/probe_tool.py`（新增） | `probe_database` 工具封装 |
| `app/agent/planning.py`（新增） | 轻量 AnalysisPlan：复杂问题一次模型调用产出 JSON（目标/指标/维度/时间范围/知识要点/步骤/预期产出），失败自动降级为无计划；`render_plan()` 注入系统提示 |
| `app/agent/graph.py` | 新增 `planner` 节点（第一轮工具后触发、每题仅一次）；`tool_limit` 改为**强制一次无工具总结**收尾并写 `termination_reason`；系统提示注入计划与剩余轮数 |
| `app/agent/tools/registry.py` | ① 数据源选择改为**能力路由**（能力优先于业务域关键词，自动模式可切换、手动模式只报告缺口）；② 元数据问句重定向到 `probe_database`；③ 业务 SQL 从"每轮 1 次"改为**最多 3 次且必须不同子问题**，同问题重复检测；④ Schema/指标检索增加本轮缓存，重复调用直接复用；⑤ `capabilities()` 改为真实 Schema 驱动 |
| `app/agent/tools/source_tool.py` | 数据源枚举改为运行时注册表驱动 |
| `app/agent/state.py` | 新增 `sql_generations` / `sql_history` / `probe_results` / `probe_cache` / `schema_cache` / `metrics_cache` / `analysis_plan` / `capability_snapshot` / `capability_gap` / `termination_reason` |
| `app/agent/service.py` | `AgentResult` 增加 `partial` 状态与探查/计划/终止字段；终止原因不再被 skill 覆盖；探查结果永不进入 `sql/rows` |
| `app/agent/prompts/{system,planner}.py` | 真实数据源清单、能力缺口必须如实说明、探查优先、SQL 预算纪律、剩余轮数 ≤1 直接作答 |
| `app/web/static/chat.js` | 新增 `partial` 状态分支：明确"部分完成 · 未跑完全部分析"，仅有探查结果时提示"不能作为经营结论" |
| `app/skills/sql_skill.py` | 单请求默认上限 80k/240s → **200k/480s**（AW 486 列全 Schema 单次生成约 2.3 万 prompt，80k 只够 3 次调用） |
| `app/commands/ask.py` | 新增 `--max-tokens` / `--max-seconds`，不再硬编码 80k |
| `.env` | 追加 `ENABLE_ADVENTUREWORKS=1`（否则前端与 Agent 都看不到该数据源；删掉该行即可回退） |

## 3. 修复前后的调用链路

**修复前（9 次决策 / 143.5s / 仅日期范围）**

```
search_metrics(fail) → select(enterprise_sales) → search_metrics → inspect_schema
→ run_text_to_sql(MIN/MAX 日期，烧 5.6 万 token) → run_text_to_sql(被拦)
→ build_visualization → run_text_to_sql(被拦) → tool_limit → status=success
```

**修复后（案例 C 实测）**

```
select_data_source(能力路由命中 adventureworks)
→ search_metrics → inspect_schema
→ probe_database(date_range)：2022-05-30 → 2025-06-29，last_complete_year=2024
→ [planner] 结构化计划注入
→ run_text_to_sql(单条 SQL：州×大类 × 2024/2023 × 销售额/去重订单/历史成本/毛利/毛利率/同比)
→ build_visualization → 最终回答（含口径说明与缺失说明）
```

关键差别：探查不占 SQL 预算、SQL 允许一次算全、选库一次到位、终止状态真实。

## 4. 真实在线回归（AdventureWorks）

命令统一为：

```bash
DEFAULT_LLM_MODEL=kimi-k3.1-pro ./.venv/Scripts/python.exe -m app.cli ask \
  --config config/local/adventureworks-smoke.toml --database <adventureworks|auto> \
  --max-tokens 260000 --max-seconds 600 --question "<问题>"
```

| 案例 | 数据源 | 结果 | 决策 | SQL 生成 | 耗时 | 行数 | Agent 侧 token |
|---|---|---|---|---|---|---|---|
| A 各类别销售额排名 | adventureworks | ✅ success | 7 | 1 | 127.5s | 4 | 149,322 |
| B 州×类别 销售额 + 去重订单 | adventureworks | ✅ success | 6 | 1 | 142.7s | 100 | 123,792 |
| C 原始复杂问题（auto，修复前） | adventureworks（自动路由） | ✅ success | 8 | 1 | 345.0s | 97 | 156,428 |
| C2 原始复杂问题（auto，修复后复跑） | adventureworks（自动路由） | ✅ success | 9 | 2 | 648.2s | 97 | 151,710 |

成本全貌：四次成功运行的 Agent 侧合计 58.1 万 token；SQL Skill 侧（DeepEye 六阶段）
在同期窗口合计约 116 万 token——**其中包含案例 A 首次运行因 80k 预算熔断的三次失败尝试**
（每次约 14 万），这部分是已修问题的一次性沉没成本。修复后单案例的 Skill 侧约 14 万
（1 次 SQL）/ 约 46 万（2 次 SQL，C2 实测窗口）。

- 案例 A 实际 SQL：`SELECT pc."Name", SUM(CAST(sod."LineTotal" AS REAL)) ... GROUP BY`，
  结果 Bikes 94,651,172.70 / Components 11,802,593.29 / Clothing 2,120,542.52 / Accessories 1,272,072.88。
- 案例 B 实际 SQL：`SalesOrderHeader JOIN SalesOrderDetail JOIN ... StateProvince / ProductCategory`，
  含 `COUNT(DISTINCT d."SalesOrderID")`，100 行。
- 案例 C 实际 SQL：CTE + 窗口函数一次算全 2024/2023 双年指标，97 行，
  列为 `StateName / CategoryName / Sales2024 / Orders2024 / Cost2024 / GrossProfit2024 / GrossMargin2024 / Sales2023 ...`；
  回答明确写了"2024 年为最近完整自然年（数据覆盖 2022-05-30 至 2025-06-29，2025 不完整）"。
- 三次运行均未使用 `reference_sql`，全部为模型实际生成 SQL。

### 4.1 回归中发现并修复的两个真实缺陷

1. **`last_complete_year` 只校验了年初覆盖**，把"数据只到 2025-06-29"的 2025 年判成完整年。
   已补年末覆盖校验（`>= 该年 12-01`），现在 AW 返回 **2024**，与模型自身判断一致。
2. **「明确业务域」关键词启发式压过能力判定**：问题含"销售/订单"即强制
   `enterprise_sales`，把模型正确选择的 `adventureworks` 判为错误（案例 C 首次运行白耗一轮）。
   已改为：能力要求优先，若该业务域库无法满足能力则忽略该启发式。
   修复后 C2 复跑：`select_data_source` 一次命中（不再出现两次），
   `probe_database` 直接返回 `last_complete_year=2024`，计划已生成，
   2 次 SQL 分别按年与按排名计算，97 行结果，status=success。

## 5. 前端任务状态修复

- 后端新增 `status = "partial"`，仅在**确有产出**（探查结果或查询结果/可视化）且触发终止条件时使用；
  纯空跑到上限仍为 `error`。
- `termination_reason = "tool_limit"` 与 `capability_gap` 随结果返回，
  `failed_stage` 不再被 skill 覆盖。
- `chat.js` 新增 `partial` 分支：标题"部分完成 · 未跑完全部分析"，
  仅有探查结果时明确"本次仅完成数据库事实探查，不能作为经营分析结论"，
  并列出能力缺失项。**不再出现"仅返回日期范围却显示分析完成"的组合。**
- `AgentResult` 新增 `probe_results` / `analysis_plan` / `sql_generations` / `termination_reason`，
  中间探查与业务结果彻底分离（`sql/rows` 只承载业务 SQL）。

## 7. 剩余限制

1. **AdventureWorks 需要 `CONFIG_PATH` 指向 AW 配置**（`config/local/adventureworks-smoke.toml`），
   因为值索引构建在该配置的 `store_root_path` 下；用默认配置启动时 AW 的 SQL 会在
   `prepare` 阶段报"需要先构建值索引"（这是既有的防脏索引设计，不是本轮引入）。
2. 单次 AW SQL 仍需约 12–16 万 token（486 列全 Schema + 六阶段重发上下文），
   三轮 SQL 上限意味着极端问题的成本上限约 45 万 token/请求。
3. 计划节点只对长问句/多要求问题触发（规则判定），复杂但提问很短的问题可能不触发计划。
4. 仍未做：SQL 语义验证器（口径正确性）、跨库联邦查询、Planner 的多轮重规划。
5. **业务口径正确性未独立校验**：C2 的最终结果表是「州×类别×年度」明细（97 行，含
   `OrderYear`），回答中的「各地区 Top-3」「增长但毛利率下降」是模型在解释层二次筛选，
   没有第二条 SQL 独立复算。执行成功 ≠ 口径正确，这一点仍需人工或用 SQL 验证器确认。
