# 实习面试讲解稿

## 30 秒版本

这是一个基于 LangGraph 的企业数据分析 Agent。我把开源 DeepEye-SQL 作为底层 Text-to-SQL 引擎，新增 ChatOpenAI 工具规划、业务口径混合 RAG、Schema 检索、只读 SQL 执行、自动图表和 Web 对话入口。项目不宣称提出新算法，重点是把研究代码改造成可评测、可观测、可安全演示的应用。

## 3 分钟版本

1. **问题**：普通 Text-to-SQL 只生成 SQL，不理解企业指标口径，也缺少多轮交互、安全执行和结果展示。
2. **架构**：LangGraph 让 LLM 根据系统 Prompt 和工具结果自主规划；工具包括业务口径检索、Schema 检查、Text-to-SQL Skill 和可视化。DeepEye-SQL 在 Skill 内负责值检索、Few-shot、Schema Linking、生成、修订和选择。
3. **RAG 优化**：业务指标从纯关键词升级为关键词 + 云向量 + 加权重排，带分数解释、缓存和故障降级。15 题开发集 Recall@3/MRR 从 0.567/0.567 提升到 1.000/1.000。
4. **工程化**：SQLite 使用只读 URI、`query_only` 和 authorizer 三层保护；每次请求记录阶段耗时、token、失败阶段和工具轨迹，并设置 token/时间熔断。
5. **评测**：完成 50 题、5 数据库三档 Text-to-SQL 消融；另有 14 题 Agent 专项、HR 6 题真实结果评测和 88 项离线测试。HR 6/6，接入后销售回归 1/1；Agent 14/14 是失败题增量回归，不表述为新模型整批成绩。
6. **边界**：系统是本地单用户演示应用，不适合公网多租户；业务口径 RAG 使用自建小规模开发集，不能当作生产泛化结论。

## 常见追问

### 为什么需要 Agent，不直接写固定工作流？

固定工作流适合确定路径，但用户可能闲聊、修改图表、追问上一轮结果或请求写操作。LLM 负责判断是否调用工具以及调用顺序；安全、SQL 执行和图表规则仍由确定性代码约束，避免把所有责任交给模型。

### 为什么主要优化 RAG，而不是长期记忆？

Text-to-SQL 的主要风险是指标定义、字段和值没有接地，因此先用 RAG 改善正确性。记忆侧只实现了 SQLite Checkpointer、历史会话和任务状态持久化，解决重启恢复与多轮追问；长期用户画像和跨会话语义记忆对实习演示收益较低，明确不做。

### 为什么使用 ChatOpenAI？

它提供标准消息、工具绑定、token usage 和 OpenAI 兼容端点适配，LangGraph 可以直接消费原生 `tool_calls`。模型创建集中在工厂中，上游 Text-to-SQL 的旧 LLM 封装只保留在 Skill 内部，边界清晰。

### 这个项目的创新点是什么？

不是模型或论文算法创新，而是应用创新和工程创新：把批处理研究代码封装成单问题 Skill；加入可解释混合 RAG、Agent 工作流、MCP、只读执行、用量观测、对话前端和可复现评测。

### 评测结果为什么不是 100%？

评测报告保留真实失败和外部服务故障。小规模题集的 100% 也不能证明泛化；更重要的是能定位失败属于意图、口径、Schema、SQL 还是模型服务，并能通过回归测试验证修复。

## 推荐现场顺序

1. 用“你支持哪些经营指标”展示闲聊和能力工具。
2. 用“按月统计 2026 年销售额趋势”展示完整工具链和折线图。
3. 追问“改成柱状图，不要重新查询”展示多轮状态复用。
4. 打开评测页展示混合 RAG 对照、Agent 专项评测和 50 题消融。
5. 最后主动说明单进程、无鉴权、开发集规模小等边界。
